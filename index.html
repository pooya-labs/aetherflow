Durable workflows.
Engineered for recovery.

AetherFlow is a workflow control plane for systems that cannot afford to forget what they were doing. Its full engine combines PostgreSQL-backed execution state, recoverable workers and explicit event-delivery semantics in one Rust workspace. The public demo runs directly on Cloudflare Workers, D1 and durable Workflows—no separate API Origin required.

The platform

One control plane.
Explicit execution boundaries.

AetherFlow keeps workflow state, worker ownership and event transport separate so each part can recover without pretending failures do not happen.

01 / CORE

Rust runtime

PostgreSQL storage

03 / EVENTS

JetStream transport

Transactional outbox, stable message identity, broker acknowledgements, pull consumers and durable inbox deduplication.

04 / EXTENSIONS

WASM boundary

Versioned WIT interface, default-deny imports, fresh bounded stores and resource-limited Wasmtime execution.

Designed for failure

Recovery is an execution path.

Tests do more than assert a process starts. They stop the API, terminate a worker, remove the full broker cluster, restore durable state and verify the work continues from recorded state.

Delivery contract: AetherFlow provides at-least-once delivery. External side effects still need application-level idempotency or a transaction shared with the downstream state.

The contract

Clear guarantees.
Clear limits.

Reliable infrastructure starts by stating what it guarantees — and what remains the responsibility of the application built on top.

What AetherFlow provides

Durable coordination primitives with explicit state transitions.

  • Transactional workflow and task state in PostgreSQL
  • Lease ownership, heartbeats and monotonically increasing fencing tokens
  • Outbox publication and inbox-backed logical deduplication
  • Tenant-scoped authorization and forced row-level security
  • Recoverable worker and broker paths verified by integration tests

What your application still owns

Distributed execution cannot make an arbitrary external side effect transactional by itself.

  • Idempotency for payments, emails and other external side effects
  • Secrets, TLS certificates and production NATS credentials
  • Shared ingress throttling across API replicas
  • Production backups, PITR and owner-approved RPO/RTO
  • Deployment topology, SLO targets and on-call ownership
Developer workflow

Start with the source.
Run the infrastructure locally.

The repository includes a pinned Rust toolchain and a loopback-only PostgreSQL 18 / three-node JetStream development stack. Use disposable data only.

01 / Clone and prepare
git clone https://github.com/pooya-labs/aetherflow.git
cd aetherflow
rustup toolchain install 1.99.1 --profile minimal --component rustfmt --component clippy
The repository pins its compiler and formatting/lint components for repeatable builds.
02 / Start local dependencies
docker compose --env-file .env.example up --detach --wait
docker compose ps
Development fixture only. The sample values and loopback plaintext database must never be reused in a network deployment.
03 / Verify the workspace
cargo +1.99.1 fmt --all -- --check
cargo +1.99.1 clippy --workspace --all-targets --locked -- -D warnings
cargo +1.99.1 test --workspace --locked
cargo +1.99.1 build --workspace --release --locked
Database and JetStream integration suites have additional disposable-service environment variables in the development guide.
04 / Explore the API
cargo run -p aetherflow-server
cargo run -p aetherflow-cli -- --help
curl --fail http://127.0.0.1:8080/health
The server starts in health-only mode without database configuration. Follow the development guide before using durable routes.
