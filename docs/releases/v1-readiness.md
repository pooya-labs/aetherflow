# AetherFlow 1.0.0 release readiness

**Release target:** v1.0.0  
**Current state:** Not released · M08 production engineering remains open  
**Last reviewed:** 2026-11-09

AetherFlow already has a versioned v1 control-plane API, but that does not make the complete platform a stable 1.0.0 release or a production-ready service. This checklist is the release gate. Keep workspace crate versions at 0.1.0 until the gates are closed; do not publish a 1.0.0 tag merely because the API path contains /v1.

## Separate no-Origin serverless deployment track

A free serverless profile is now implemented separately from the Rust/PostgreSQL/NATS release target:

- **Cloudflare Free:** Worker `aetherflow-free-runtime` is deployed on the account's `workers.dev` subdomain, with the `aetherflow-free` D1 database (WEUR) and `aetherflow-execution` Workflow binding. The live Workflow API smoke test completed an `echo` task and confirmed the final workflow/task state plus event history in D1. Temporary test records and Workflow instances were removed afterwards.
- **Dashboard routing:** direct GitHub Pages visits bootstrap a short-lived Cloudflare session and use the Worker directly. No custom domain, VPS, separate API Origin, PostgreSQL connection or NATS server is used on this path.
- **Apps Script:** the V8 Web App wrapper, `google.script.run` bridge, private Spreadsheet adapter, quotas and manifest are in `apps-script/`. The owner provided a [live Web App URL](https://script.google.com/macros/s/AKfycby-RppnSarisz26pfexeZLjd-LD_FTmE8q6Ea3JtFLkl4iAfuyCCLX61p92nNZLlWyr/exec) on 2026-11-08, and the page responds with the expected AetherFlow title. The owner then confirmed `Read-only · Connected · synthetic demo data` and four seeded workflow records, including `demo-index-003` and `demo-retry-004`. This verifies bridge bootstrap, Script Properties, private Spreadsheet access, and workflow-list reads. The selected-run inspection surface remains intentionally read-only. A separate `Store persistence test` action now sends one bounded storage-only workflow and event through the Apps Script bridge; the task is not executed. Chromium QA [42521608664](https://github.com/pooya-labs/aetherflow/actions/runs/42521608664) passed all 12 desktop/mobile tests, including the submit/refresh/read-back and pending-state fixture. The owner completed that live test: `gas-smoke-61f2c9e5308d4978ae69d39ddf6bf5d6` remained after a full-page reload. A source correction now keeps future Apps Script storage-only runs/tasks `pending`; it is committed in the repository but still needs to be copied into the Apps Script editor and deployed as a new Web App version. Google anonymous-deployment availability is account/region dependent; do not enable billing as a workaround.
- **Execution scope:** Cloudflare profile supports bounded built-in task handlers only (`echo`, `collect`, `uppercase`, `sha256`, `add`, `fail_once`). The Apps Script profile is a bounded low-volume demo/control-plane adapter and does not run task code. Neither profile supports arbitrary user code, the Rust WASM ABI, NATS JetStream semantics, or production tenant identity; they are not full feature parity with the Rust runtime.
- **Free-tier guards:** internal defaults cap launches at 25/day, tasks at 20/workflow with at most 3 attempts/task, reserved Workflow steps at 2,000/day, API reads at 12,000 requests/day, API mutations at 2,500 requests/day, 60 new sessions/day, 250 reads/session, 60 mutations/session and 50 retained workflows/workspace. Before admission, the Worker reserves up to `12 + task_count × max_attempts` steps (72 for the largest accepted definition). This is below Cloudflare Workflows Free's 3,000 steps/day. API caps count requests, not D1 rows; Cloudflare D1 Free separately allows 5 million rows read/day and 100,000 rows written/day. Provider quotas are shared across account workloads and still need monitoring.
- **Boundary:** this does not close the separate `cloudflare-gateway/` production reverse-proxy gate. That older gateway still lacks a reachable Rust HTTPS Origin and origin-bypass tests. The no-Origin serverless runtime is a separate deployment track, not the production ingress gateway for the Rust API.

This track improves usability where an external Origin is unavailable, but it does **not** close the M08 deployment topology, PostgreSQL PITR/RPO/RTO, production NATS server controls, production SLO ownership, or independent security-review gates. Do not publish Rust workspace crates as 1.0.0 based solely on the serverless runtime smoke test.

## Explicit non-goals and claims to avoid

- Do not claim universal exactly-once execution. Delivery is at-least-once; application-level idempotency or a transactional integration is required for external side effects.
- Do not call a passing CI restore drill production PITR.
- Do not describe process-local rate limiters as cluster-wide quotas.
- Do not label the control plane production-ready until the deployment, operations, recovery, and ingress gates above are satisfied.
